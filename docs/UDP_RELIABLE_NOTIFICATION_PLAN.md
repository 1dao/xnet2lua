# UDP 与可靠通知功能规划

日期：2026-11-08
状态：实施中。第 1 阶段实现完成并通过本地验收；第 2 阶段已完成独立通知机制，完整 wire format 和安全封装尚未交付。逐阶段进度、实际接口及未定决策见第 15 节。

## 1. 目标与边界

为游戏通信增加独立、可选的 UDP 能力，并在其上实现服务端主动发起的 Ping/Pong 通知确认机制、客户端 RPC 请求接纳与结果查询机制。

硬约束：

- 功能默认关闭，显式增加编译选项才启用。
- 关闭时不编译 UDP 专属实现、不注册 UDP 脚本接口，不引入新增依赖或启动行为。
- 不改造现有 TCP/TLS 数据流协议，不改变其默认行为。
- C 网络核心保持语言无关，允许 Lua、xjs，以及未来的 Python 绑定使用。
- 通知只确认到达，不确认业务执行；RPC 框架负责请求重试、去重、结果缓存和查询，业务负责执行及副作用幂等。
- 同一会话同时只有一份正在等待确认的通知数据。
- 需要可靠到达的下行业务消息统一进入通知通道，包括普通可靠通知、RPC 接收确认、执行结果及结果查询应答；连续移动状态使用独立的 MOVE 数据报路径，允许丢包。
- RPC 接收确认允许短暂延迟；等待期间已有执行结果时，直接发送结果即可。
- 周期性 Ping 作为空闲心跳；实际发送业务触发的 Ping 后，顺延下一次空闲心跳。
- 移动暂停走可靠通知；开始及连续移动可由后续 MOVE 状态恢复。客户端按运动版本判断旧状态是否仍适用，但对有效可靠报文仍回复 Pong。
- 公共报文处理顺序为编码、按需压缩、认证加密、UDP 发送；接收按反向流程处理，认证成功后才解压和接纳。

首版不直接扩展成通用的可靠有序传输协议。广播、组播、批量系统调用、滑动窗口及 QUIC 接入不属于首版必要范围。

本文的“可靠”表示约定范围内的确认、重试与去重；不能仅凭这些机制声称已经提供安全传输。认证、密钥建立、加密、防重放及路径验证需完整设计和验证后才能作出相应安全承诺。

## 2. 当前项目基础

当前主线网络路径为 `xsock → xchannel → 脚本绑定`，事件通知由 `xpoll` 提供。

| 模块 | 当前职责 | 本次处理方式 |
| --- | --- | --- |
| `xsock.c/.h` | 跨平台 socket 操作，当前主要面向 TCP | 复用基础类型、非阻塞和关闭操作；UDP 专属操作保持独立 |
| `xpoll.c/.h` | epoll、kqueue、WSAPoll、poll，以及可选的 io_uring 提交接口 | 复用就绪通知，不增加独立事件循环 |
| `xchannel.c/.h` | 字节流缓冲、分帧、部分发送和 EOF | 不用于 UDP 数据报管理 |
| `xlua/lua_xnet.c` | Lua 网络对象和接口注册 | 仅增加受编译宏保护的接入点 |
| `xthread`、`xrouter` | 线程消息和业务分发 | 可供会话路由使用，不赋予其 UDP 可靠性语义 |
| `xsession.lua` | 基于连接的会话处理 | 保持现有行为，新增数据报会话模块 |

本地 xjs 分支的网络绑定同样使用 `xchannel/xpoll`，并在 actor 上维护网络对象。因此 UDP 绑定也需要遵循各语言运行时、线程及 actor 的生命周期，不能只维护一个进程级脚本对象。

UDP 的数据报边界和来源地址必须保留。即使 `xchannel` 使用 raw 模式，其内部仍按照字节流处理，不能直接承担此职责。

## 3. 独立构建与编译宏

第 1 阶段已按仓库构建风格实现以下选项：

| 项目 | 已实现值 |
| --- | --- |
| Make 构建选项 | `WITH_UDP=0`，默认值为 0 |
| C 编译宏 | `XNET_WITH_UDP=0/1` |
| MSVC 构建入口 | `build.bat udp ...` 显式启用，默认关闭 |

已实现用法：

```sh
make all WITH_UDP=1
make test WITH_UDP=1
```

编译要求：

1. UDP 核心源文件仅在启用时进入静态库；语言绑定仅在启用时进入对应 runner。
2. 使用 `#if XNET_WITH_UDP` 保护声明、引用和接口注册；宏未定义时按 0 处理。
3. UDP 功能不依赖 `WITH_HTTP`、`WITH_HTTPS`，也不要求新增第三方网络库。公共压缩和认证加密依赖需显式列入启用构建，不能因为复用 TLS 库中的算法而要求开启 HTTPS；默认关闭构建不增加这些依赖或初始化行为。
4. 公共脚本模块按需加载，不在现有 runner 启动流程中自动创建 socket、定时器或会话。
5. 关闭构建中，脚本通过相关接口是否存在来检测支持情况；不注册会在调用时才报“未启用”的占位 UDP 接口。
6. 构建选项切换必须避免旧目标文件复用；需要配置依赖或按配置隔离产物。仅在命令行改宏、但继续使用旧产物，不满足验收要求。
7. 测试清单随开关选择；默认关闭构建仍运行原有测试。

首版使用一个总开关控制本次 UDP 功能。公共脚本协议模块可以随源码分发，但只有启用 UDP 且被应用显式加载时才工作。

## 4. 分层方案

数据报层及 Lua 绑定已按以下分层落地；公共安全协议、业务接入及后续多语言机制仍属于待定方案。

| 层 | 职责 | 不承担的职责 |
| --- | --- | --- |
| C 数据报层 | socket 收发、地址、事件通知、收包预算、统计和资源释放 | 玩家身份、Redis、角色迁移、通知业务语义 |
| 公共报文编解码层 | 编码封装、按需压缩、认证加密、解压上限和报文大小检查 | 角色归属及游戏操作；密钥和会话材料由上层生命周期管理 |
| 语言绑定 | 字节串与地址转换、回调、运行时及 actor 对象生命周期 | 通知路由和角色归属 |
| 脚本会话及 RPC 框架 | Ping/Pong、可靠下行队列、MOVE 最新值合并、超时重发、去重、RPC 接纳与结果缓存、会话恢复及状态导入导出 | 决定角色在哪个进程、执行游戏操作 |
| 游戏业务层 | 身份认证接入、角色归属、迁移协调、持久化和通知有效期 | 重复实现底层重发状态机 |

### 4.1 首版建议

C 层已增加独立的 `xudp.c/.h`，Lua 侧已增加独立绑定实现，现有绑定文件只做条件接入。公共脚本层已实现与 wire format 无关的通知机制；完整可靠通知协议及 RPC 生命周期仍待公共安全路径及业务策略定案，不能视为已完成游戏业务接入。

脚本框架不是某个业务脚本的私有实现，但它会依赖相应语言运行时。纯 JS runner 若首版也要使用该协议，需要提供 JS 框架实现，或提前采用公共 C 协议模块；不能默认依赖 Lua。

### 4.2 后续可提取的公共 C 状态机

如果多语言都需要完全相同的通知协议，可以将稳定的纯机制提取为独立 C 模块：提交字节数据、匹配确认、触发重发、导出及恢复状态。

该模块不持有语言对象，不调用 Redis，也不决定角色迁移。发送、保存、恢复和归属变化通过明确接口交给上层。是否首版就提取，取决于是否要求 Lua、JS 同期交付；不必为未来可能的 Python 支持提前实现全部绑定。

## 5. C 数据报层

第 1 阶段已实现的 Lua 接口：

```lua
udp = xnet.udp_bind(host, port, handler, options)
udp:sendto(data, ip, port)
udp:sockname()
udp:close()
udp:is_closed()
udp:stats()
```

接收回调为 `on_datagram(udp, data, ip, port)`，每次交付一个完整数据报。客户端可以绑定端口 0，由系统选择本地端口。当前仅实现数值 IPv4 单播，地址表示为 IPv6 扩展保留空间；主机名 DNS 和 IPv6 尚未实现。

实现约束：

- 非阻塞收发，每轮限制处理数量，避免抢占线程消息和定时器。
- 零长度 UDP 报文合法；超长数据报不能截断后当作完整通知交给脚本。
- 发送返回成功只表示本机接受发送，通知是否到达由 Pong 判断。
- 首版可直接返回 `would_block` 等发送错误；如增加缓冲，必须按完整报文连同目的地址保存，并设置容量上限。
- 单个不可达目的地址不能通过复用 TCP 的错误处理直接关闭共享 UDP socket；需要消费并分类系统错误，明确 Windows UDP reset 的处理策略。
- 正常关闭时立即解除事件注册并关闭 fd；脚本对象内存回收与 fd 关闭分开处理。
- 线程或 actor 退出前清理其持有的 UDP 对象；覆盖回调内关闭及重复关闭。
- 启用 io_uring 的构建中，首版 UDP 仍可使用就绪路径；现有提交接口不能直接提供未连接 UDP 所需的来源地址信息。

服务端通常以一个 socket 服务多个客户端。玩家会话超时不关闭这个共享 fd。UDP fd 不会因为空闲或客户端退出而自动回收。

### 5.1 报文边界与内部消息边界

UDP 自带数据报边界。两次 `sendto` 产生两个数据报，每次 `recvfrom` 最多取出一个数据报；不使用 TCP 的 2/4 字节外层长度头解决分帧问题。

拟议外层逻辑结构为“协议类型、会话/安全头、协议内容”，通过类型区分 `PING`、`PONG`、`MOVE`、`RPC_REQUEST`、`RPC_QUERY` 等。具体字节布局尚未定案。

一个 Ping 中包含多个内部通知时，内部边界由编码格式或每条消息长度给出，例如 MessagePack 数组、Protobuf 重复消息，或 `[消息长度][消息体]` 列表。是否沿用现有 2/4 字节消息长度头属于内部格式兼容决定，不是 UDP 分帧要求。

### 5.2 就绪事件与循环收包

底层可读事件数与数据报数量不一一对应。两个包都已排入 socket 时，可能只产生一次可读通知，但读取并交付两次 `on_datagram`。

一次事件中循环 `recvfrom`，直到暂无包可读、达到本轮预算或遇到需处理的错误：

- 返回非负长度：处理一个完整数据报；返回 0 是合法空数据报。
- 返回暂不可读错误：POSIX 的 `EAGAIN/EWOULDBLOCK`，Windows 的 `WSAEWOULDBLOCK`，结束本轮。
- 中断等可重试条件按平台分类处理；其他错误进入错误处理路径。
- 达到本轮预算先让出执行时间。在现有水平触发就绪路径中，下轮继续处理；若以后改为边沿触发，需安排主动续读，不能假设仍有下一次边沿通知。

不得根据“没有内容”把合法空包误判为 EOF，也不能假设两次发送必然产生两次系统事件。UDP 本身可能丢失、重复或乱序，框架回调按实际接收的数据报执行。

### 5.3 压缩、认证加密与接纳顺序

```text
发送：
逻辑消息 → 编码/装包 → 按需压缩 → 认证加密 → sendto

接收：
recvfrom → 最小头部及长度检查 → 认证解密 → 按标志限量解压
         → 完整协议解析 → 轮次/状态去重与接纳 → 业务处理
```

该公共路径服务于可靠通知、MOVE、RPC 和相关确认报文，避免业务各自实现一套封装。最小明文头可用于定位会话和密钥，但在认证前不信任其内容，不据此修改会话地址或执行游戏操作。

约束如下：

- 使用成熟实现提供的 AEAD 认证加密；认证失败时丢弃数据，不交给解压器和业务，不回复该通知的 Pong。
- 协议类型、会话及密钥标识、传输包序号、压缩标志等需要防篡改的明文头字段纳入附加认证数据。具体字段和算法套件待定。
- 小 MOVE、Pong 等可以不压缩。标志、算法与是否启用由协议明确约定；每包独立可恢复，不让解压依赖可能丢失的前一包。
- 设置独立的解压输出上限，不因报文声明的原始长度就无界分配；压缩、加密及认证标签开销都计入最终报文预算。
- 每次新加密满足同一密钥下 nonce 唯一性要求；`ping_id` 在重发时不变，不能直接作为每次新加密的唯一序号。
- 建议保存不可变的逻辑编码/压缩内容，每次发送尝试分配新的传输包序号并重新认证加密。这样重发保留原 `ping_id` 和通知内容，而安全封装可以变化；不要求密文字节完全相同。
- 每个方向的密钥、序号和防重放状态独立管理。切网不随意重置，跨进程交接时也不能在同一密钥下重用 nonce；无法安全延续时重新建立安全上下文。
- 防重放处理允许约定范围内的乱序；通知去重按 `ping_id` 进行。合法重发应能进入通知去重路径并再次生成 Pong，避免将所有重发直接过滤而无法完成确认。

接收方完成认证、限量解压、整份解析并接纳数据后，才回复匹配 Pong；不等待游戏业务或动画执行完成。有效重复轮次不重复交付业务，但再次回复 Pong。已过期运动通知的跳过规则见第 6.7 节。

## 6. 通知协议：仅一份当前待确认数据

### 6.1 已确定的行为

- 服务端主动发送 Ping，Ping 可以附带通知数据。
- 发送时从待发送通知队列取出数据并打包；打包成功后，这些通知从待发送队列移除。
- 打包结果保留为当前待确认数据，直到收到匹配的 Pong。
- Pong 只表示到达和接纳，不表示执行完成。
- Pong 未到之前，不发送下一份通知数据。
- 超时重发当前数据，期间到达的新通知进入待发送队列。
- 普通通知、RPC 接纳确认、RPC 执行结果及结果查询应答都作为下行消息交给同一队列打包。

不需要维护多个在途可靠批次或可靠发送窗口。本文使用 `current_data` 表示唯一一份当前可靠数据；此限制不阻止独立 MOVE 数据报发送。

### 6.2 仍需每轮 Ping 的标识

虽然同时只有一份数据，仍需要 `ping_id` 区分不同轮次：重发 A 可能产生多个 Pong，服务端收到第一个后发送 B，迟到的 A 的 Pong 不能回收 B。

拟议逻辑报文如下，具体编码待定：

```text
PING：会话标识、ping_id、通知数据、认证及防重放字段
PONG：会话标识、ping_id、认证及防重放字段
```

`ping_id` 标识通知确认轮次。它与加密所用的传输包序号、RPC 请求 ID 分别管理；具体安全封装不在本文直接规定。

### 6.3 状态与流程

```text
pending_notifications  待发送通知队列
current_ping_id        当前确认轮次
current_data           当前已打包数据；无在途轮次时为空
next_retry_time        下次重发时刻
next_heartbeat_time    下次空闲心跳时刻
last_valid_receive     最后一次收到有效客户端消息的时间
```

```text
待发送：[A、B、C]
    ↓ 打包成功，转移所有权
当前数据：PING #10，包含 A、B、C
待发送：[]
    ↓ 新通知到达
待发送：[D、E]
    ├─ #10 超时：重发同一轮次、同一通知内容
    └─ 收到 PONG #10：释放当前数据，随后打包 D、E
```

客户端首次接纳该轮数据后回复 Pong；重复收到同一轮时再次回复 Pong，不重复向业务交付。客户端先完整校验并取得通知数据所有权，再确认，不等待业务执行。

空 Ping 同样使用轮次标识并等待匹配确认。等待期间的新通知留在队列中，避免将同一个 `ping_id` 从空数据改成有数据。这样会增加等待延迟，需要在验收中评估。

“打包所有通知”受单包长度预算约束：单次取出预算内的完整通知，其余继续留队列。单条通知超过上限时显式失败或使用另行定义的大消息通道；首版不隐式拆包后复用同一个确认。

### 6.4 时间与容量

- 空闲心跳周期、数据重试间隔、会话超时和恢复窗口分别配置。
- 有通知且没有在途轮次时可以立即发送，无须等待空闲心跳周期。
- 重试采用受控的退避，设置总期限；待发送及未确认数据均设置容量上限。
- 会话超时后的通知去向由业务策略决定：丢弃、恢复状态同步，或持久化等待重连。
- 统计本地重发、重复、队列满及丢弃；不能直接将这些计数宣称为真实网络丢包率。

### 6.5 统一可靠下行通道

需要可靠到达的下行数据由框架打包，业务仅提交逻辑消息。例如：

```text
PING(session_id, ping_id, [
    NOTIFY(protocol_id, payload),
    RPC_ACCEPTED(rpc_id),
    RPC_RESULT(rpc_id, success_or_failure, result),
    RPC_STATUS(rpc_id, status)
])
PONG(session_id, ping_id)
```

这是逻辑结构示例，具体编码、字段宽度和安全封装待定。Pong 统一确认整份数据到达，不能用它替代某个 RPC 的执行结果。

同一会话只有一份当前可靠数据，因此前一轮未确认会阻塞后续可靠下行业务消息。独立 MOVE 数据报不受此等待限制。必须在性能验收中评估 RPC 结果延迟，并通过队列容量、重试期限和失联处理限制积压。首版不为 RPC 接收确认另建绕过此队列的快速通道。

单轮等待只限制下行通知。客户端上行 RPC 请求和结果查询可以独立发送；客户端按 `rpc_id` 维护各调用，不必把所有 RPC 串行成一个调用。客户端收包和 Pong 响应也不能被业务执行或等待 RPC 返回阻塞。

握手、路径验证、恢复会话和 Pong 属于协议控制消息，需明确其独立处理路径；会话尚未恢复时不能依赖已阻塞的业务通知通道完成恢复。

### 6.6 空闲心跳顺延

周期性 Ping 表示“空闲到期后发送”，不再使用不受业务发送影响的固定时刻表。业务触发 Ping 并被本地 socket 接受发送后，重新计算：

```text
next_heartbeat_time = now + heartbeat_interval
```

例如周期为 10 秒：0 秒发送 Ping，原定 10 秒发送空心跳；6 秒因业务实际发送新一轮 Ping，下次空闲心跳改为 16 秒。这里的数值仅说明顺延规则，不是已验证的默认参数。重发实际发出后也可重新计算空闲期限，但继续受当前轮次的重试和总超时规则约束。

调用发送接口但仅入队，或本地发送失败，不能视为实际发出 Ping。当前轮次尚未确认时，新业务只入队，不改变当前数据，也不推迟当前轮次的重发期限。

| 计时项 | 更新依据 | 不允许的更新依据 |
| --- | --- | --- |
| 空闲心跳期限 | 实际发送 Ping | 单纯入队或发送失败 |
| 当前轮次重发期限 | 当前轮次实际发送尝试与重试策略 | 新业务入队、反复调用 Ping |
| 会话失联期限 | 收到通过验证且符合防重放规则的客户端消息 | 服务端自己发送或重发 |

本地发送失败需安排有界的后续发送尝试，避免忙循环。重试次数和总期限不能因重发而无限重置。过期或重复控制包不能被无限用于延长会话存活。

收到匹配 Pong 后，队列有消息就立即进入下一轮；队列为空则等待空闲心跳期限。空闲期限已到且无在途轮次时才发送新的空 Ping。

MOVE 单向发送不作为顺延 Ping 心跳的依据，避免持续发送位置却一直得不到客户端响应。收到通过验证的有效客户端消息可以按活跃规则更新失联时间，但不能代替当前可靠轮次的匹配 Pong。

### 6.7 移动同步与可靠暂停

其他玩家的连续位置、方向、速度采用最新状态覆盖旧状态，不进入可靠通知重发队列。共享 UDP socket，逻辑上区分两条路径：

```text
可靠通知：通知队列 → PING → 等待 PONG → 回收
连续状态：合并最新值 → MOVE → 允许丢包，由后续快照恢复
```

拟议脚本发送形式为 `udp:sendto(encode_move(state), session.ip, session.port)`；这不是当前已有实现。此处 `encode_move` 代表完整的公共编码及安全封装路径，不能绕过认证加密而裸发业务内容。共享未连接 socket 使用 `sendto` 指定目的地址；不是 TCP 字节流发送接口。

MOVE 不等待 Pong，不重发历史位置。本地发送暂时受阻时，仅保留该实体最新待发送状态，或按明确策略丢弃；不得无界缓存历史轨迹。忽略丢包不等于忽略包长、速率、权限及本地错误统计。

建议的逻辑字段为：

```text
MOVE：实体标识、实体代次/场景版本、motion_version、state_seq/server_tick、
      位置、速度、方向、当前运动状态
暂停通知：实体标识、实体代次/场景版本、motion_version、暂停位置及状态
```

开始运动、暂停、再次开始等状态切换由权威服务器递增该实体的 `motion_version`；持续采样在同一运动版本内用 tick/序号区分新旧。跨进程迁移继承版本，不依赖各机器墙上时钟比较顺序。若采用时间戳，应使用明确的服务器权威时间域并解决重启、迁移和回退问题，首版优先使用版本。

已讨论采用的策略：

- 开始及持续运动：后续仍持续发送自包含 MOVE，首包丢失可由后续新状态纠正。
- 暂停/停止：在暂停后可能不再产生 MOVE，因此放入可靠通知队列，等待 Pong 并按规则重发。
- 客户端已接收更新运动版本：跳过旧暂停的状态应用，仍对有效 Ping 回复 Pong。
- 客户端没有更新版本：接纳并应用暂停到指定位置，之后忽略更旧 MOVE；若后续收到新运动版本，再更新运动状态。
- 同一版本内按状态序号处理位置新旧；跨场景或实体重新创建后，旧代次数据不能作用于新对象。

例如：

```text
开始 v10 → 暂停 v11 放入 PING #100（丢失）→ 再次开始 v12
    ├─ 客户端收到 MOVE v12：以后收到重发的暂停 v11 时跳过，回复 PONG #100
    └─ MOVE v12 及后续包都丢失：暂停 v11 继续可靠重发；客户端可暂时暂停，
       等新 MOVE 真正到达后恢复到新状态
```

服务器产生或发出了新 MOVE，不证明客户端已经收到。首版不因此提前取消旧暂停，也不作废在途 Ping；收到匹配 Pong 才回收。如果未来增加客户端明确回报新运动版本的机制，再独立评估取消过期运动通知的优化，不能取消同包内尚有效的 RPC 结果或其他通知。

一份 Ping 可以包含多条消息，旧暂停的跳过仅作用于该消息，其他有效消息照常接纳。同一 `ping_id` 的逻辑内容仍保持不可变。扣道具等不可覆盖事件不能沿用“版本过时就跳过”的规则。

客户端可通过插值及有时间上限的外推平滑显示。MOVE 首版使用独立可解析的快照；若以后改为增量，需明确已知基准和丢包恢复，不能默认前一包已到达。尚未建立实体或场景基准时，采用有界暂存、丢弃或重新同步策略，不无界等待。

开始运动依赖后续状态恢复，不承诺该次切换单独可靠到达。若业务要求每个切换事件均被确认，则开始和暂停都需可靠处理，连续位置仍可使用 MOVE。

### 6.8 接收顺序与业务完成顺序

Pong 仅表示收到，不表示上一条业务已经完成。单份等待把尚未发送的数据留在服务端，但不能自动保证异步业务串行完成；一份 Ping 内部也可能有多条有依赖的通知。

客户端为有先后关系的消息维护串行执行序列：同步处理在前一条返回后执行下一条；异步处理则等待前一任务完成再推进。仅按序启动多个异步任务不足以保证完成顺序。收包及回复 Pong 不等待这些任务。

例如“创建道具”之后“装备该道具”应在同一有序业务执行序列中处理。若服务器必须知道客户端执行完成后才能推进，则另行定义业务完成确认，不改变现有 Pong 的接收确认语义。

可靠事件和 MOVE 分属不同交付路径，不提供跨路径的全局到达顺序。运动版本、实体代次及场景版本用于明确可覆盖状态之间的先后关系。

## 7. 客户端 RPC：接纳确认、执行结果与查询

### 7.1 两阶段反馈

RPC 区分“请求已被接纳”和“业务执行已经结束”。请求接纳确认及执行结果均通过第 6 节的统一可靠下行通知通道送达。

```text
客户端 → 服务器：RPC_REQUEST(rpc_id, protocol_id, arguments)
服务器：校验、登记请求、纳入待执行队列
服务器：安排延迟接纳确认，转交业务执行
服务器 → 客户端：RPC_ACCEPTED 或直接 RPC_RESULT
服务器：业务结束，保存成功或失败的最终结果
服务器 → 客户端：RPC_RESULT(rpc_id, result)

客户端等待结果超时：
客户端 → 服务器：RPC_QUERY(rpc_id)
服务器 → 客户端：处理中 / 最终结果 / 未知或已过期
```

`ACCEPTED` 的边界为请求已校验、登记并纳入待执行处理流程，不是底层 socket 刚收到字节。队列满、认证失败或参数非法时明确拒绝。框架需要处理登记成功但业务投递失败的情况，不能确认后无记录地丢弃请求。

若承诺跨进程崩溃恢复，需要在确认前可靠保存请求及可恢复的待执行状态；内存接纳只承诺所定义的进程存活或主动迁移范围。

### 7.2 延迟接纳确认与结果合并

接纳后短暂等待，例如 10ms；具体值做成配置：

```text
接纳请求 → 开始确认等待
    ├─ 等待期内业务结束：取消待生成的 ACCEPTED，加入 RESULT
    └─ 等待期结束仍无结果：加入 ACCEPTED
                                  ↓
                            业务随后结束
                                  ↓
                              加入 RESULT
```

延迟确认不会延迟业务开始执行。定时器和业务完成事件需在同一请求状态上协调：

- `ACCEPTED` 尚未生成：结果直接取代确认。
- `ACCEPTED` 已进入待发送队列、尚未打包：可将其移除或替换为结果。
- `ACCEPTED` 已进入当前待确认数据：保持该轮编号和内容不变，将结果排入后续队列。

10ms 表示决定生成确认的等待时间，不保证消息在 10ms 内实际发出。当前轮次未确认时，确认及结果都可能排队；客户端请求重试参数需要容忍这段等待。

### 7.3 请求身份与服务端状态

去重键包含经过认证的角色或逻辑会话身份、调用命名空间及 `rpc_id`。重发、查询、切网及归属迁移沿用同一逻辑调用身份；不能每次网络重试生成新 ID。

登记应先于业务执行，确保业务协程等待期间的重复请求也不会创建第二次执行。相同 ID 携带不同协议或参数时拒绝，并通过保存请求摘要等方式识别冲突。

| 服务端状态 | 重复请求或结果查询的处理 |
| --- | --- |
| 等待执行 / 执行中 | 返回已接纳或处理中，保持原任务 |
| 已成功 / 已失败 | 返回保存的同一个最终结果 |
| 明确拒绝且未执行 | 返回拒绝原因 |
| 未知 / 已过期 | 明确说明无法确定历史结果，不宣称未执行 |

查询只读取状态或重发已保存结果，不重新触发业务。副作用操作仍通过业务幂等键、事务等手段处理崩溃期间“业务已提交、结果尚未保存”的窗口；请求记录不能单独保证跨故障只执行一次。

### 7.4 客户端等待与重试

客户端分别管理：

- 接纳确认等待：未收到确认或结果时，受控地重发相同请求及 `rpc_id`。
- 执行结果等待：已确认接纳但尚无结果时，超时改为查询状态；查询可退避重试，并设置总等待期限。
- 通知接收确认：对每轮 Ping 独立回复 Pong，不等待该 RPC 或其中其他业务完成。

若结果先于接纳确认到达，直接完成调用并停止相关重试；迟到确认、重复结果和重复查询应答都不能再次完成或恢复同一协程。客户端等待超时不代表服务器取消执行。

### 7.5 结果缓存与下行副本生命周期

Pong 允许释放该轮通知的发送副本，但 RPC 请求状态及结果缓存按独立保留策略管理，不能因发送副本被确认就立刻遗忘整个 RPC。

缓存保留窗口需覆盖约定的客户端查询、重试和会话恢复窗口，并设置条数及字节上限。若提前释放大结果，需明确客户端已接纳结果后还能查询什么，并保留所需去重记录，避免旧请求再次执行。

重复请求或查询不应无界增加相同应答：待发送队列中可合并相同 RPC 状态/结果，已打包的当前数据保持不可变。

游戏状态更新是否允许丢弃旧值、重要通知和 RPC 结果是否持久化，由业务恢复承诺明确规定。

### 7.6 技能业务

技能释放作为普通权威业务请求走可靠 RPC：客户端传入稳定 `rpc_id`、技能标识、目标或施法位置，服务器校验角色状态、冷却、资源、距离等条件，返回成功或失败。重发沿用相同调用 ID，避免重复扣资源或生成技能。

`RPC_ACCEPTED` 仅表示接纳；释放成功的 `RPC_RESULT` 通常表示技能已启动，不必等待整个动画、弹道或后续伤害过程结束。命中、伤害、中断和结束等必须到达的事件通过可靠通知下发，由业务明确定义其含义和顺序。

瞄准方向、预览位置等连续状态可另用允许丢包的最新状态路径；正式释放、取消及中断请求需要可靠处理。客户端可以预测表现，释放判定和伤害结算以权威服务器为准。

## 8. 切网、恢复与角色迁移

### 8.1 会话身份与地址分开

会话不能仅以 IP 和端口作为身份。切网后客户端从新地址主动请求恢复，通过认证和新路径验证后，服务端才更新地址。恢复请求需有新鲜性校验，防止重放和旧路径迟到包造成地址回退。

当前通知数据、`ping_id` 及客户端去重记录属于逻辑会话。仅地址变化时保留它们，在新路径继续重发。客户端未完成 RPC 及其 ID、服务端请求状态和结果缓存也继续归属于原逻辑调用。

### 8.2 切网不必然要求角色迁移

如果新入口可以根据稳定角色标识转发到旧角色所在进程，则只更新入口和路径。若现有分配策略要求角色跟随新入口进入不同线程或进程，则执行角色归属迁移。

这两个方案需要结合实际入口路由决定，不能在 UDP C 层固定。

### 8.3 需要迁移时的交接

建议由脚本框架和业务协调以下流程：

1. 认证恢复请求，定位角色现有归属。
2. 暂停旧归属上的新业务和通知生产，协调暂停期间的新请求。
3. 交接角色状态、实体代次和运动版本、待发送队列、当前数据、当前轮次及后续编号状态，以及 RPC 待执行记录、执行状态、已完成结果和必要的去重信息；协调安全上下文、密钥与传输序号，避免 nonce 重用。
4. 使用归属版本或租约等机制转移所有权，阻止旧实例继续写入和发送。
5. 新归属加载状态，完成新路径验证，继续重发原来的当前数据。
6. 客户端按原轮次去重并回复 Pong，新归属确认后释放当前数据。

迁移中收到的 Pong 和新通知需要串行归入一次交接结果，不能在快照之后被旧实例独立清除而丢失，也不能出现两个写入者。

迁移时同样需要协调 RPC 接纳确认定时器和业务完成回调。进行中的任务不能仅靠复制“执行中”标志就恢复：应明确由旧归属完成并转交结果，或在安全点交接，或根据业务幂等机制恢复执行。新入口需要能够定位原调用记录，不能因请求落到新进程便把相同 RPC 当作新请求执行。相应期限在恢复时按剩余时长或明确的跨进程时间规则重建，不能直接复制仅在旧进程有意义的单调时钟数值。

角色归属版本用于协调所有权，不能简单地在每次迁移时重置通知轮次和客户端去重记录。

### 8.4 Redis 与故障恢复范围

Redis 是可选的共享状态存储，不是 UDP 实现依赖。

- 仅支持进程存活期间的主动迁移：可以在暂停后交接状态快照。
- 要求进程突然退出后仍保留通知和 RPC：需要可靠持久化通知、请求、确认及结果状态，并处理保存、发送、业务提交、结果记录、确认、删除之间的故障窗口。
- 客户端进程重启：原有内存去重记录可能消失，需要明确是否恢复接收进度，或创建新会话并同步业务状态。

Pong 只保证约定意义上的客户端接收，不保证客户端崩溃后仍保留数据。跨重启的恢复承诺必须单独定义。

## 9. 客户端协议兼容需要明确的内容

“兼容”指是否沿用已有客户端约定，不表示当前已有 UDP 协议。

| 内容 | 例子 |
| --- | --- |
| 编码格式 | 现有 Protobuf 或 MessagePack 消息能否原样放入通知数据 |
| 消息分发 | 原有 `protocol_id + payload` 如何组成通知列表 |
| 身份认证 | 已登录客户端凭什么恢复原会话，凭证如何验证 |
| 编号表示 | Lua、JS、Python 一致表达 `ping_id`，避免数值表示差异 |
| 状态顺序 | 实体代次、运动版本与采样序号的表示，旧暂停与新 MOVE 的比较规则 |
| 安全封装 | 协议版本、压缩标志、长度预算、AEAD 套件、密钥建立、nonce 和防重放窗口 |
| RPC 关联 | `rpc_id` 的命名空间、重试保持规则、接纳确认和结果状态的表示 |
| 客户端接收状态 | 切网和进程重启分别保留哪些去重信息 |
| 恢复策略 | 会话仍有效时继续原轮次，过期后如何重新登录和同步 |

外层负责会话与轮次，内部通知可以继续使用已有业务消息格式。完整 wire format、安全封装及字段宽度在公共协议接线前确定；独立数据报层和不依赖这些决定的纯机制可先实施。

现有 `xframe_aead` 的接收检查会拒绝小于等于已接收最大序号的数据。若用于 UDP，需要另行设计允许合理乱序的防重放处理，不能直接假设现有连接加密封装适用。

| 阶段 | 交付内容 | 验收重点 |

| 1 | 默认关闭的构建开关、独立 C UDP 层及首个语言绑定 | 开关隔离、数据报边界、预算收包、生命周期 |
| 2 | 公共报文编解码、单份当前数据的可靠下行框架、空闲心跳及测试客户端 | 压缩与认证边界、超时重发、编号匹配、去重和心跳顺延 |
| 3 | MOVE 与可靠暂停、客户端 RPC、延迟确认、结果缓存及查询 | 状态覆盖、运动版本、去重执行、确认与结果合并、技能业务接入 |
| 4 | 会话认证接入、新地址验证及恢复接口 | 切网后继续原通知与 RPC，无旧路径回退 |
| 5 | 结合实际入口实现归属路由或迁移，按需求接入持久化 | 单写入者、通知及 RPC 交接一致性、明确故障恢复范围 |
| 6 | 按交付需求增加 xjs 等语言支持，评估公共 C 状态机 | 跨语言协议一致性、无隐含 Lua 依赖 |

需要同期交付多个语言时，相应调整第 2、3、6 阶段，先确定公共机制的实现位置。可靠传输机制编码前先参考第 13 节列出的 ENet 实现，不将 ENet 自动加入构建依赖。

## 11. 验证计划

- 构建隔离：开关关闭时无 UDP 专属源文件、接口或自动启动行为；启用后可独立于 HTTP/TLS 构建；反复切换开关无旧产物污染。
- UDP 基础：二进制、空数据报、多客户端、端口 0、报文边界、超长报文和错误分类。
- 收包循环：一次就绪事件内读取多个数据报，每包单独交付；暂无数据退出、合法空包继续处理、预算耗尽后能继续读取且不饿死其他任务。
- 编解码：外层不依赖 TCP 长度头；内部多消息边界完整，畸形长度及截断报文被拒绝。
- 压缩与认证：压缩和不压缩报文往返、明文头或密文篡改、认证失败不解压、不回复确认；异常原始长度和解压输出上限。
- 重发与安全序号：逻辑轮次不变但每次新加密使用唯一 nonce，合法重发仍能获得 Pong；乱序及重复包处理符合窗口策略，迁移和重启不造成 nonce 重用。
- 生命周期：回调中关闭、重复关闭、actor/线程退出、fd 复用及资源统计恢复基线。
- 确认协议：请求丢失、Pong 丢失、重复和迟到 Pong；旧确认不能释放新数据。
- 通知队列：打包失败不丢数据、等待期间新增通知、空 Ping 在途、超限和单条超长通知。
- 客户端语义：同轮次重复到达只交付一次，但每次重复均能再次确认；确认不等待业务执行。
- 统一可靠下行：普通可靠通知、接纳确认、RPC 结果及查询应答共用同一轮次确认；前一轮丢包时不会修改在途内容，积压受上限约束；MOVE 可独立发送。
- 空闲心跳：业务实际发出 Ping 后顺延；仅入队和发送失败不顺延；新业务不会推迟当前轮次重试，主动发送不会延长失联期限。
- 单向移动同步：持续发送 MOVE 不会无限推迟需要客户端响应的 Ping，也不能代替未收到的匹配 Pong。
- 运动版本：开始、暂停、再次开始；暂停首次丢失、新 MOVE 全部丢失、重发暂停迟到；仅当客户端已有新运动版本时跳过旧暂停，仍确认其可靠轮次。
- 状态数据：MOVE 丢失、重复和乱序，实体重新创建及切场景，暂停位置恢复；历史 MOVE 不积压，新状态发送成功不提前取消旧暂停重试。
- 混合消息：同一 Ping 中旧暂停过期而 RPC 结果仍有效时，只跳过暂停，不丢弃整包或修改重发内容。
- 业务顺序：同步及异步依赖操作的客户端串行执行；Pong 不等待动画或任务完成，协议接收顺序不被误当作异步任务完成顺序。
- 技能：释放请求、接纳确认或结果丢包，重发不重复扣资源或生成技能；启动结果与命中、伤害、结束通知的语义区分。
- 延迟接纳确认：等待期内完成只发送结果；确认已排队但未打包时可合并；确认已在途时结果进入后续轮次；定时器和业务完成同时触发时无重复终态或漏结果。
- RPC 重复：请求或接纳确认丢失、同 ID 重发、执行中重复到达、同 ID 不同内容；有效保留窗口内只创建一次业务执行。
- RPC 结果查询：结果丢失、查询及查询应答丢失、处理中退避查询、未知及过期记录、缓存容量和保留窗口。
- RPC 客户端：结果先于接纳确认、重复结果、迟到结果、超时后查询；同一调用只完成一次，等待超时不隐式取消服务器执行。
- RPC 生命周期：Pong 仅释放发送副本，所需结果缓存及去重记录继续保留；同一结果的重复查询不会无界扩张下行队列。
- 切网恢复：新地址认证及验证、当前数据继续发送、旧恢复请求不能回退地址。
- 角色迁移：交接期间的新通知、Pong、RPC 请求和完成回调，旧归属停止写入，目标恢复后延续原轮次及调用身份；进行中的任务不被盲目重新执行。
- 若承诺崩溃恢复：分别注入保存前后、发送后、确认后及删除前后的故障，验证所承诺的持久化行为。
- 平台与运行时：现有平台矩阵覆盖启用和关闭两类构建；Lua 后端及交付的 JS runner 分别验证。
- 压测：通知确认延迟、单轮等待造成的队列积压、内存上限、压缩加密开销、MOVE 发送预算及线程定时器延迟；据此调整预算和重试参数，不预设比 ENet/KCP/QUIC 更快。

## 12. 公共协议与业务接入前仍需定案的事项

1. 首版是否要求 Lua 与 xjs 同期提供可靠通知框架，是否因此直接采用公共 C 状态机。
2. 新入口能否转发到原角色归属，哪些情况必须迁移线程或进程。
3. 会话恢复、身份认证和新地址验证沿用什么登录凭证体系。
4. 恢复承诺是否包含服务器进程崩溃、客户端进程重启，以及对应持久化策略。
5. 通知及 RPC wire format、长度预算、编号表示、时间参数及队列满策略；延迟接纳确认的约 10ms 等待需配置和验证。
6. RPC 查询与去重记录的保留窗口、结果存储上限、记录过期和迁移中任务的处理策略。
7. 压缩算法和阈值、解压上限、AEAD 套件及密钥建立、明文头认证、nonce 和跨进程防重放状态的具体实现。
8. MOVE 同步节奏及预算、实体代次与运动版本的编号规则、客户端实体基准恢复和串行执行接口。

这些事项保持为显式决策，不将讨论中的候选方案误写为已有实现或已确定需求。

## 13. ENet 参考与 KCP、QUIC 对比

### 13.1 ENet 参考评估

已检查本地 `3rd/enet`，远程指向官方 `lsalzman/enet`，检查时提交为 `5a9c537`。本次是实现机制检查，不是完整安全审计，也不据此声明库没有漏洞。

ENet 提供可靠 UDP 机制，但其文档明确将应用身份认证和加密留给上层。因此“可靠送达”不等于具备本方案需要的会话认证、路径验证和安全封装。

| 参考点 | 本地实现位置 | 对本方案的价值 |
| --- | --- | --- |
| 序号确认与回收 | `protocol.c` 的 `enet_protocol_handle_acknowledge`、`enet_protocol_remove_sent_reliable_command` | 按轮次匹配确认，防止迟到确认释放新数据 |
| RTT 及方差估计 | `protocol.c` 的 `enet_protocol_handle_acknowledge` | 为重试参数提供实现参考 |
| 超时与退避 | `protocol.c` 的 `enet_protocol_check_timeouts` | 受控重发、总期限和断开处理 |
| 报文所有权 | `packet.c`、`peer.c` | 明确复制、持有、确认释放和失败清理 |
| 聚合与容量控制 | `docs/design.dox`、`protocol.c`、`include/enet/enet.h` | 通知装包、报文大小和积压限制 |

其当前接收路径会检查来源 IP 和端口，不匹配的普通 peer 数据报被丢弃；不能直接承担本方案的切网会话恢复。角色迁移、Redis 状态和 RPC 结果交接同样需要上层实现。

首版保持原生 UDP 与单份当前数据方案，选择性参考上述机制。若以后需要多通道、窗口和分片重组，再评估直接接入 ENet；届时应重新划分其可靠确认与本方案 Ping/Pong 的职责，避免叠加两套相同目的的传输重试。即使使用传输层确认，RPC 执行状态、结果查询和业务幂等仍属于上层职责。

该参考评估不改变默认关闭、编译宏控制的要求，不新增 ENet 编译依赖。

### 13.2 与 KCP、QUIC 的边界

本方案包含应用会话、通知和 RPC 框架，以及简化的单轮等待可靠发送机制。ENet、原始 KCP 核心和 QUIC 主要提供传输能力；不能替代业务接纳、执行结果及角色迁移状态管理。

| 项目 | 本方案 | ENet | 原始 KCP 核心 | QUIC |
| --- | --- | --- | --- | --- |
| 可靠在途数据 | 一份当前可靠数据 | 发送窗口及通道 | 发送窗口 | 多包及多流 |
| 排序 | 可靠轮次，内部业务按约定串行；MOVE 按版本覆盖 | 同一可靠通道有序，各通道独立 | 同一 KCP 会话有序交付 | 流内有序，不同流独立交付 |
| 允许丢包的状态 | 独立 MOVE | 不可靠有序消息，可与可靠通道区分 | 需外层单独提供路径 | 可协商使用 DATAGRAM 扩展 |
| 安全封装 | 本次规划加入，套件和密钥建立尚待实现 | 认证和加密由上层提供 | 认证和加密由外层提供 | 集成基于 TLS 1.3 的安全机制 |
| 切网 | 应用认证、路径验证及恢复 | 本地实现检查来源地址，需上层恢复 | 地址及恢复由外层处理 | 提供协议级路径迁移，受实现及配置限制 |
| RPC 接纳、结果查询及持久化 | 本方案明确设计 | 上层实现 | 上层实现 | 上层实现 |
| 角色跨进程迁移 | 上层协调状态及所有权 | 上层实现 | 上层实现 | 上层实现，不由路径迁移自动完成 |

单轮等待会把尚未发送的可靠消息留在服务器；窗口机制可提前传到客户端，再按序交付。两者都需要客户端明确异步业务的执行顺序，传输确认不是业务完成确认。

例如每轮承载 1,200 字节业务数据、RTT 为 100ms 时，单轮等待的理想吞吐约为 12KB/s/会话，尚未计入丢包、处理时间和其他开销。这是条件示例而非实测或默认包长。高延迟及丢包下需要验证可靠消息积压；独立 MOVE 不受该可靠窗口限制，但仍共享网络带宽和发送预算。

如果以后采用 ENet/KCP/QUIC 承担可靠传输，应重新评估单轮等待和网络重试的必要性，同时保留具有业务含义的接纳确认、结果查询、去重与跨重连恢复。传输 ACK 不直接等同于脚本框架已接纳消息；需要这个边界时可以保留应用确认，但不必叠加两套同目的的丢包重传。

实际 Lua 接口：

```lua
local u, err = xnet.udp_bind("127.0.0.1", 0, {
    on_datagram = function(udp, data, ip, port) end,
    on_error = function(udp, system_error, fatal) end, -- 可选
}, { max_datagram = 65507, recv_budget = 64 })
local ip, port = u:sockname()
local ok, reason, system_error = u:sendto(data, ip, port)
local stats = u:stats()
u:close()
assert(u:is_closed())
```

`host` 为数值 IPv4；`nil`/空串绑定 `0.0.0.0`，允许端口 0。不在收发路径进行阻塞 DNS。`max_datagram` 范围 1..65507，`recv_budget` 范围 1..65536；上述默认值仅属于原始数据报层，65507 不是通知协议推荐包长或已确定 MTU。发送失败原因包括 `would_block/too_large/invalid_address/closed/system_error`，系统错误单独返回；原生错误码可从 `stats.last_error` 获取。UDP 启用时 `xnet.get_stats()` 额外提供当前线程的 `udp_count/udp_object_count`；关闭时无这些字段、接口或 UDP metatable。

- `step(now)` 使用调用者提供的单调毫秒时间；本地失败设置有界下次尝试，成功发送才顺延空闲心跳，重发退避且轮次总期限和最大尝试数不重置。过期后保留数据供上层选择后续策略。
- `ack(id, now)` 只释放实际发出过的匹配轮次；队列非空立即尝试下一轮。迟到/重复 Pong 不释放新数据或更新失联时刻。
- `new_receiver(options)` 提供 `receive/take`；先完整解析并取得不可变消息的队列所有权，再调用 Pong hook。业务从 `take()` 取出后自行串行执行；重复/旧轮次不重复交付，但再次确认。解析失败或队列满不确认。
- 所有容量、重试、心跳和期限参数必须显式提供，尚未将示例值写成产品默认值。编号由 `next_id/compare_ids` 注入，暂不决定跨语言字段宽度；编号不可重复或回退。
- `pack/decode/send_ping/send_pong` 是待接公共编码及安全传输的明确接口，不内置 wire format 或裸发路径。`send_ping` 接收的是不可变逻辑编码/压缩内容，每次实际发送必须由将来的传输层分配新安全序号并认证加密。接收方法只能在认证、防重放及有界解压之后调用；`valid_receive` 不能用于重复/过期控制包。
- 模块显式加载时检查 UDP 支持，不创建 socket 或定时器。测试使用声明为测试专用的字符串编码及编号，仅验证纯机制；未据此完成认证/压缩或真实协议客户端验收。

实现前复核本地 ENet 的确认匹配、报文所有权、超时及指数退避路径；未加入 ENet 构建或运行依赖。

2. 通知/RPC/control 的 wire format、编号表示和最终数据报预算；时间、满队列、结果缓存及过期策略。
3. 压缩算法/阈值/输出上限；AEAD 套件、密钥建立、nonce、方向及跨进程防重放状态。
